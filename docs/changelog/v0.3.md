# v0.3.x Summary (0.3.4 → 0.3.18)

The `0.3.x` releases predate SMF's established three-repo coordinated release process, so there are no standalone release notes in the doc repo. This page looks back over the minor versions in reverse chronological order, with content consolidated from git commits and the skill repository's `known_gotchas.md`.

---

## v0.3.18 — Pipeline hygiene batch (M2-M4)

Three MEDIUM-severity hygiene defects, found in the same review round as 0.3.17's H1-H4 and released separately to keep 0.3.17 from getting bloated. All are "silently wrong data / silently discarded user intent / errors far from the real cause".

- **M2** `CreditModelPipeline._fit_woe` copied `warm_start_score_col` with `.to_numpy()` without a length check. A `dropna` / filter / reindex on either side would cause row misalignment. The new `Pipeline/_common.copy_column_length_checked` enforces the check.
- **M3** `RejectInferencePipeline._run`, when combining `train_prescore=True` with an already-existing `score_col`, silently overwrote the user's preset score column. It now issues a `UserWarning` that explicitly reports the column name about to be overwritten.
- **M4** `_fit_prescore`, when the approved frame was empty, produced a confusing error deep inside sklearn `stratify`. It now raises a `ValueError` directly in the pre-check, with the three counts approved/target-observed/total.

---

## v0.3.17 — Pipeline hardening batch (H1-H4)

Four HIGH-severity "silently wrong data" defects. Zero API changes; everything is a tightening of behavior.

- **H1** The LR branch of `CreditModelPipeline._fit_models` modified the user's `cfg.model_params["lr"]` dict. It now copies first, then pops.
- **H2** `oot_col == 0` evaluated False for all string flags (`"0"` / `"1"` / `"train"` / `"test"`), swallowing the entire training set into OOT. The new `Pipeline/_common.split_oot_by_flag` uniformly goes through `pd.to_numeric(errors="raise")`, so numeric strings still work and non-numeric content raises explicitly.
- **H3** The implicit prescore path of `RejectInferencePipeline` (triggered when `score_col` is not in the columns) did not validate `target_col` in `_validate_input`. Both paths are now checked up front.
- **H4** `oot_frac + ri_validation_frac ≥ 1` in `RejectInferencePipeline` silently leaked OOT into validation. It is now a hard assertion at the start of `run()`.

---

## v0.3.16 — RI `_weight` sample_weight fix

`RejectInferencePipeline` named the sample-weight field it passed to the downstream fitter `wgt`, but sklearn needs `sample_weight`. The parameter was silently ignored, and the weights had no effect at all. It was changed to the correct `sample_weight`.

---

## v0.3.15 — Missing-rate screening stage 0

`Feature_Screen.feature_screen` gains a `missing_rate_threshold` parameter, serving as the first screen before PSI / IV / correlation. Variables with a high missing rate are dropped directly before WOE binning, keeping the downstream WOE fit from being thrown off by extremely sparse columns.

---

## v0.3.14 — Weighted corr NaN + empty-stage audit

- Weighted correlation (`_weighted_corr`) returns NaN rather than raising for all-NaN / single-value columns, so later stages can skip them explicitly.
- Each Screen stage output gains an "empty-result audit": when a stage ends with an empty selected set, it records the whole run of prior counts, making it easy to locate which threshold cleared out the candidates.

---

## v0.3.13 — `run_modeling_from_validation` orchestrator

A top-level wrapper: one entry point that runs FVP → generates a `FeatureScreeningArtifact` → hands off to `CreditModelPipeline` with WOE reuse enabled. It closes out the five-step refactor of 0.3.9-0.3.12.

---

## v0.3.12 — Weighted `feature_screen` reuses WOE bins

Adds `_weighted_woe_bins_screen` / `_weighted_iv_from_assigned_bins`. Previously, weighted PSI/IV/correlation fell back to equal-frequency binning with a warning; from this version, if a WOE engine has already been fitted upstream, the weighted path directly reuses its bin boundaries, with values consistent with the unweighted path.

---

## v0.3.11 — CM handoff from the FVP screening artifact

`CreditModelPipeline` gains three fields: `screening_artifact` / `feature_validation_result` / `reuse_screening_woe`. The WOE engine fitted by FVP is reused directly by CM, avoiding duplicate fitting and result drift.

---

## v0.3.10 — FVP selection mode + FeatureScreeningArtifact

`FeatureValidationPipeline` gains `selection_enabled` / `selection_params` / `weight_col`, runs the shared `feature_screen` after the WOE fit, and exports `selected_features` and the new dataclass `FeatureScreeningArtifact` (for handoff to CM).

---

## v0.3.9 — Unified `feature_screen` kernel

A new module, `Modeling_Tool/Feature/Feature_Screen.py`, merges the screening logic that CM and FVP previously maintained separately. `weighted_feature_screen` and `CreditModelPipeline._feature_selection` both now delegate to the shared API. From then on, the weighted and unweighted paths share one config class and one IV/PSI/corr implementation.

---

## v0.3.7 / v0.3.8 — Pipeline persistence + first weighted screen

- `0.3.7` added `explain_outputs` persistence (SHAP / LIME / permutation results written to files instead of staying only in memory).
- `0.3.8` introduced the first version of `weighted_feature_screen` and wired it into Pipeline selection (for IPTW/PSM scenarios).

---

## v0.3.6 — `woe_fit_query` + `extra_eval_datasets`

`CreditModelPipeline` gains two fields:
- `woe_fit_query`: a filter expression applied at WOE fit time, which can exclude certain populations without affecting downstream eval.
- `extra_eval_datasets`: evaluation sets appended beyond the standard train/test/OOT (commonly used in FT scenarios — naturally approved samples are used only for eval, not for fit).

These two fields came into being to meet the frequent business need of "exclude a population from the fit but keep it in the eval", which previously could only be handled by splitting frames by hand.

---

## v0.3.4 / v0.3.5 — Initial stable release

Introduced monotone WOE bin-boundary filling, the Pipeline skeleton, and the split into six modules: Core / Sample / Feature / Model / Eval / Explainability. All later versions iterate incrementally on this skeleton.
