# v0.7.1

This minor release formally tightens the governance defaults that were previously opt-in and explicitly announced in 0.6.x, completes the G06-2 categorical VIF gate, and fixes the categorical-feature regression in the corr stage of the unweighted path (R1). After upgrading, if you need to keep the old basis, pass the old values explicitly; only the parameters called out below still keep 0.6.x behavior through an explicit `None`.

!!! note "Version note: why there is no v0.7.0"
    `0.7.0` was found to have the R1 regression during pre-release field validation (a downstream pre-run from source), and that version number was voided before release. `0.7.1` is the **first released version** of the `0.7.x` line, with contents = all the changes originally planned for 0.7.0 + the R1 fix and its hardening. Behaviors described as "from 0.7.1" all take effect from this version.

## Tightened Default Governance

### OOT Usage Boundaries

- `synthesize_missing_oot` now defaults to `False`: when there is no real OOT, a copy of OOS is no longer labeled as OOT. CMP no longer creates an `"oot"` split; FVP keeps an empty OOT representation, and the relevant downstream steps skip it.
- CMP's default `evaluation_splits=["ins", "oos"]`, so default model evaluation, charts, and Excel no longer consume OOT; `extra_eval_datasets` remains a separate eval-only input.
- `search_eval_splits` defaults to `["oos"]`, so LR search and Optuna no longer put OOT in the eval sets for candidate tuning; `backward_validation_split` remains `"oos"`, and `backward_report_splits` defaults to `[]`, so the round-by-round backward report does not read OOT.
- A real OOT can still enter the corresponding stages through explicit configuration; the consumption-point hard gate of `forbidden_splits` and the `split_governance` / model-metadata audit fields remain in effect.

### WOE and Evaluation Direction

- The FVP `woe_fit_scope` default changes from `"all"` to `"post_missing_gate"`: the selection-grade missing-rate gate runs first, and the top-level WOE is then fitted on the surviving variables, so a single high-missing variable cannot invalidate the whole group of WOE artifacts. Pass `"all"` explicitly if you need the historical basis.
- The `MonotoneWOEBinner.refine_min_n_bins_policy` default changes from `None` to `"warn"`: if `refine_dtree()` pushes the number of ordinary bins below `min_n_bins`, a visible warning is left; `"enforce"` / `"raise"` can still be used for stricter governance needs, and an explicit `None` turns the check off.
- `gains_ascending` now defaults to `True`: scores ascend and bin 1 is low-score/low-risk. The gains summary, weighted gains, and evaluation distribution plots use the same direction, removing the direction drift between the table and chart paths of the old version; an explicit `False` uniformly descends, and an explicit `None` keeps the historical direction of each 0.6.x path.

## G06-2: Categorical VIF Gate

`selection_params` gains `vif_use_woe_bins`, defaulting to `False`, and preserves the compatibility semantics of the raw numeric VIF:

- Raw VIF sends only numeric survivors to statsmodels; string, object, and other non-numeric columns stay in the selection result and are not wrongly dropped by VIF. A `UserWarning` is issued, and the excluded columns are durably recorded in the selection summary / VIF stage artifact; when there are too few numeric columns, the gate is skipped as `skipped_insufficient_numeric`.
- bool and pandas nullable numeric/boolean are converted to floats only inside the VIF matrix, and plain NumPy numeric input keeps its original behavior.
- With `vif_use_woe_bins=True`, VIF is based on the INS WOE-encoded matrix, so categorical variables can take part in the collinearity check. This path creates the adapter lazily, respects custom WOE suffixes, transforms on a copy, and gives an actionable error when a pre-fitted engine's coverage is incomplete.
- For declared categorical variables, WOE-VIF requires `woe_engine="monotone"`; the `equal_freq` `WOE_Master` does not support this categorical fit path and raises a clear error before fitting.

FVP passes this field through to the screening config and records the final value in `selection_config_snapshot`.

## R1: Categorical-Feature Regression in the corr Stage of the Unweighted Path

Pre-release field validation of 0.7.0 found that in unweighted (no `weight_col`) feature screening / FVP selection, when categorical features (str / StringDtype) reach the corr de-duplication stage, the whole screening crashes (`ValueError: could not convert string to float`). The root cause is that the correlation matrix of both `CorrelationFilter` classes (the base class and the WOE patch class) was always built from raw values — `corr_use_woe_bins` previously affected only the IV tie-break metric and never the matrix basis; the tightened default governance of 0.7.x lets categorical survivors actually reach the corr stage, so the latent defect surfaced (0.6.8 with the same input died later, at the VIF gate, i.e. G06-2). **The weighted path was always correct, and gets zero changes this time** — this fix precisely aligns the unweighted side with the weighted side's existing "exclude + warn + keep" semantics.

- **`corr_use_woe_bins=True` (the FVP default) and the screening binner can encode the column: mixed matrix basis.** Numeric columns stay raw (numeric-numeric de-duplication is byte-for-byte identical to the old version), while categorical columns enter the matrix as WOE-encoded values (under the original column names) and take part in de-duplication together with the other columns; exactly identical categorical twin columns are de-duplicated normally, dropping one. Columns the binner does not cover are excluded from the matrix, kept in the selection result, and given one `UserWarning` (suggesting a refit that covers the column).
- **`corr_use_woe_bins=False` or the base class: numeric-subset matrix.** Non-numeric columns are excluded + kept + one `UserWarning` (suggesting `corr_use_woe_bins=True` to let categorical columns take part in de-duplication).
- Excluded columns are **never dropped by corr**; purely numeric input keeps the old behavior byte-for-byte on both classes with zero warnings; each matrix build emits at most one warning, with no repeated warnings across iterations.
- **Unavailable engine fails loudly**: when an unsupported WOE engine object is configured and categorical columns are present, the corr stage raises a contextual `TypeError` directly (with the original error on the `from` chain), instead of silently degrading and excluding all categorical columns; column-level coverage gaps of supported engines still take the soft-warning path.
- Under `corr_use_woe_bins=True`, the weighted and unweighted matrix bases are **deliberately different** (weighted: WOE for all columns; unweighted: raw numeric + WOE categorical): this is a trade-off to keep byte-for-byte compatibility of the unweighted numeric path. The raw basis (`corr_use_woe_bins=False`) gives selections exactly identical to the weighted path under all-ones weights.

## Migration Notes

If the business really needs the old behavior restored, set the corresponding values explicitly, for example:

```python
CreditModelPipelineConfig(
    synthesize_missing_oot=True,
    evaluation_splits=["ins", "oos", "oot"],  # only when a real OOT exists
    search_eval_splits=["oos", "oot"],
    backward_report_splits=["oot"],
    gains_ascending=None,  # exactly keeps the historical direction of each 0.6.x evaluation path
)

FeatureValidationPipelineConfig(
    woe_fit_scope="all",
    monotone_woe_params={"refine_min_n_bins_policy": None},
)
```

Before explicitly consuming OOT, first confirm that it is a business-real OOT and not a copy of OOS synthesized by a historical version.
